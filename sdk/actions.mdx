## Register client-side callbacks

Use client-side callbacks for operations that belong to the current page, such as navigation or
updating in-memory application state.

```js
const actions = [
  {
    tool_id: 'clientside_callback_open_billing',
    input_schema: {
      type: 'object',
      properties: {},
      additionalProperties: false,
    },
    execute: async () => {
      router.navigate('/settings/billing');
      return { opened: true };
    },
  },
];

await window.Dubot.init({
  userId: currentUser.id,
  identityToken,
  actions,
});
```

The callback must also have a reviewed, published governance envelope in Dubot and be reachable
through a Skill capability attached to the wizard or Copilot.

The action detail shows whether the callback has been observed from the SDK. Registration supplies the schema and unlocks publishing; an unregistered or disabled callback remains unavailable at runtime. Dubot matches a registration to an action by its full tool ID, including the `clientside_callback_` prefix.

### Name the callback `clientside_callback_<name>`

Every `tool_id` you pass in `actions` must:

- start with `clientside_callback_`, for example `clientside_callback_open_billing`;
- use only lowercase letters, numbers and underscores, 64 characters at most;
- not reuse a built-in SDK tool, such as `clientside_callback_navigate`.

The SDK skips any callback that breaks these rules. It doesn't throw. It only logs a console error, for example:

```text
[dubot] skipping clientside action 'open_billing': tool_id must start with 'clientside_callback_'
```

If a callback never shows as registered in Dubot, check the browser console for this message first.

### Review a discovered callback

When the host registers a callback that doesn't match an existing action, Dubot lists it for review rather than discarding it. This is the most reliable way to create a callback action, because the tool ID and input schema come straight from your code.

<Steps>
  <Step title="Register it from the host">
    Add the callback to `Dubot.init({ actions })` and load a page where the SDK runs.
  </Step>
  <Step title="Find it in Pending review">
    Open **Actions → Pending review**. Each observed `tool_id` appears with its session count and when it was last seen.
  </Step>
  <Step title="Review and create">
    Select **Review**. Check the observed input schema, add a display name and a model-facing agent description, then select **Approve & create**. This creates a draft action that stays disabled.
  </Step>
  <Step title="Enable it">
    On the action, turn on **Enabled**. A disabled callback is never offered to the agent, even when it's published.
  </Step>
  <Step title="Attach and publish">
    Add the action to a Skill capability and publish with **Publish all**, which publishes the skill and its actions together. Then publish the wizard or Copilot that uses the skill.
  </Step>
</Steps>

## Replace callbacks when page state changes

`setActions()` uses full-set replacement semantics. Pass every callback that should be available
after the call.

```js
window.Dubot.setActions([
  openBillingAction,
  currentInvoice ? markInvoiceReviewedAction : null,
].filter(Boolean));
```

A callback omitted from the new set becomes unavailable to the assistant on the next turn.

## Execute Session API actions

<Info>
  The customer-owned Session API executor is currently delivered and reviewed during integration;
  it is not yet a stable self-service public API. Confirm its request and registry contract with
  Dubot before implementing the first authenticated operation.
</Info>

Session API actions are authored in Dubot with a method, endpoint, input schema, response mask,
risk, and execution policy. The runtime boundary is deliberate:

```text
SDK requests { tool_id, input }
  -> customer-owned first-party executor resolves the published registry
    -> executor uses the application's existing authentication
      -> customer API returns a result
        -> response mask reduces the result
          -> SDK continues the assistant turn
```

The SDK bundle does not receive an arbitrary destination from the model and should not own the
customer application's credentials. Dubot provides the first-party executor pattern during
integration so the customer's engineering team can review and ship it with the application.

## Confirmation and outcomes

Every action has an `auto` or `confirm` execution policy.

- Chat-originated confirms render in the wizard.
- End-user MCP confirms render in the page action toast.
- A decline returns a declined outcome without invoking the operation.
- Errors return a bounded failure result and appear in action activity.
- Response masks limit which returned fields reach the assistant.

## Resource Center callbacks are separate

A static Resource Center card can run a host callback without advertising that callback as an
assistant tool:

```js
await window.Dubot.init({
  userId: currentUser.id,
  identityToken,
  resourceCenterCallbacks: [
    {
      id: 'clientside_callback_contact_support',
      execute: () => supportMessenger.open(),
    },
  ],
});
```

`resourceCenterCallbacks` and `actions` are intentionally separate registries. A card callback's `id` matches the card's callback ID in the Resource Center and doesn't need the `clientside_callback_` prefix.
