Dubot organizes everything around a simple structure: small, reviewable building blocks are grouped into capabilities, and capabilities are given to an agent. Understanding these three layers is the fastest way to read the rest of these docs.

## Three layers

```text
atomic units (actions, pages, knowledge, journeys)
  -> capabilities (scoped buckets with a description of when to use them)
    -> agents (a configured assistant that is given capabilities)
```

## Atomic units

<CardGroup cols={2}>
  <Card title="Action" icon="zap">
    An operation the agent can perform through a reviewed product contract or Browserbot step. Each action carries an expected effect and a policy: act automatically, require confirmation, or remain unavailable.
  </Card>
  <Card title="Page" icon="app-window">
    A summarized inventory of a product surface: what is on it, what it links to, which semantic targets are available, and what current evidence supports the map.
  </Card>
  <Card title="Knowledge" icon="book-open">
    Help center articles and documents ingested into a single reviewable corpus per workspace. See [Knowledge](/product/knowledge) for what exists today.
  </Card>
  <Card title="Journey" icon="route">
    A reviewed goal, set of checkpoints, allowed behavior, approval policy, completion signal, and fallback. Journeys are authored and versioned, but Browserbot can adapt their route to the live product.
  </Card>
</CardGroup>

<Note>
  A journey is one building block among several, not the top-level catalog. It describes how a task is done and can reference actions, pages, and knowledge.
</Note>

## Capabilities

A capability is a scoped bucket of atomic units with a description of when it should be used. Capabilities are how a team gives an agent a coherent area of responsibility without granting open-ended access. Control includes the intended effect, permissions, action policy, completion evidence, and failure behavior.

## Agents

An agent is a configured assistant. Today the product lets a team set an agent's model, reasoning budget, and customer-facing behavior, then attach capabilities and actions after the agent is created. This is the configuration plane. How the agent behaves at runtime is described in [How Dubot works](/concepts/how-dubot-works).

<Info>
  **Available today:** creating an agent, configuring its model, reasoning budget, and behavior, and attaching capabilities and actions.

  **In development:** runtime knowledge retrieval and reusable governance controls.
</Info>
