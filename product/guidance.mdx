Guidance helps a user complete work on the live page. It can show the next control, perform supported interactions, and pause when the next step belongs to the user. Launch it from a configured Copilot conversation, a reviewed guide, or the SDK.

## Show and Do

| Mode | What happens |
| --- | --- |
| **Show** | Dubot explains and highlights controls. The user performs host clicks, typing, and selection. |
| **Do** | Dubot can automate agent-owned stages. User-owned stages still require the user's interaction and evidence of completion. |

Each saved guide has an explicit Show or Do mode. The workspace policy can be **Let the agent decide**, **Always show**, or **Always do**. With the default policy, a saved guide keeps its mode and a goal-based run chooses a mode with its plan. A forced workspace policy overrides the guide or planner choice.

The resolved mode stays fixed through reconnection, steering, and replanning. Changing mode starts a new run.

## User handoffs stay explicit

For example, a Do run can navigate to Team and open an invitation dialog. If the email field and Send button belong to the user, Dubot highlights them and waits. Do does not authorize the assistant to fill or submit those stages.

A required button handoff waits for the actual host-button click. **Skip**, a passive **Next**, an unrelated click, or a chat answer does not satisfy required user work. An explanatory tooltip can use Next without activating the underlying control. Input confirmation accepts the user's value without synthesizing a host click.

The runtime checks allowed actions and user handoffs. A click alone does not prove success: the resulting product state must still be observed.

## Two ways to start

| Start | Input | Use when |
| --- | --- | --- |
| Reviewed guide | A published guide ID | The goal, mode, start condition, and instructions have been reviewed |
| Goal-based Guidance | A free-text goal | The runtime should plan against the current page within configured constraints |

Saved guides contain a title, goal, start condition, trigger phrases, explicit interaction mode, and a plain-language guide body. Authors describe the intended task and user handoffs; the runtime resolves the current interface. Guides do not require saved CSS selectors or the older typed step composition.

## The current Guide Bar

The on-page Guide Bar keeps the active task and **Stop** control visible. A paused run can expose **Resume**; question and choice states wait for the user's answer. Typing in the bar composer can pause a running guide so the user can steer it. Failed runs expose a recovery path when available.

When a Copilot conversation launches Guidance, the panel yields space without destroying the conversation. After the run, the conversation can show the resulting completed, stopped, or failed state. A run can resume after supported navigation once the SDK initializes again.

The [SDK Storybook](https://dubot-sdk-storybook.pages.dev/?path=/story/guidance-exploratory--play-invite) demonstrates current component states with scripted fixtures. These examples do not perform work in a real customer account.

## Save, publish, and verify

[Enable Guidance](/guides/enable-guidance) for the workspace, test a safe journey, and publish the configuration. Reviewed guides have their own draft and publish lifecycle. When saving a run as a guide, review its mode and user handoffs before publishing it.

The current guide format replaces the older typed-step compatibility restriction. Do not change a user-owned step into an automated action to make a guide run. Test the intended behavior with compatible services and SDK in the target environment.

A Copilot guide card is ready only when Copilot, the guide, and Guidance are published for the same environment and the path works on the host page. Record launch, guide outcome, and observed task completion separately.

Developers can start a run through `Dubot.triggerGuidance()`. See [SDK surfaces](/sdk/surfaces#guidance) and [Turn a run into a guide](/guides/review-guidance-run).
